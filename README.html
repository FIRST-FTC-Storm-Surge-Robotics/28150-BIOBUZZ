01 / The big picture

This repository is the collection of files used to build team 28150's robot-control app for BIOBUZZ. The team writes its instructions in Java, a programming language. The app runs on the robot's controller and tells its motors what to do.

FTC means FIRST Tech Challenge, the robotics competition. FIRST provides an SDK, or software development kit: ready-made code that handles jobs such as talking to motors and receiving gamepad input. We build on that code instead of writing those parts ourselves.

You move a gamepad stick→Our code calculates motor power→The robot moves

The Driver Station is the driver's control app. It lets you select a robot program, start it, stop it, and read status messages. FTC calls a selectable robot program an OpMode. A TeleOp is an OpMode in which a person drives with a gamepad.

Our current program is called Prototype TeleOp. It drives four wheels and has a slow mode. There is no team program for driving automatically or controlling other mechanisms yet.

03 / Driving the robot

The robot uses mecanum wheels: wheels with angled rollers that let it move sideways as well as forward and backward. Moving sideways without turning is called strafing.

First gamepad controlWhat it does
Left stick, up/downDrive forward or backward.
Left stick, left/rightMove sideways.
Right stick, left/rightTurn the robot.
Hold the right bumperUse slow mode. Release it to return to normal power.

Directions are based on the robot's front. If you turn the robot around, pushing forward still moves it toward its own front, even if that is now toward you.

Slow mode limits motor commands to 40% of full power. That gives finer control, but it does not guarantee exactly 40% of the robot's usual speed.

The motor names must match

The code finds each motor by name. These names must exactly match the names in the robot's hardware configuration—the saved list of connected devices on the robot controller.

Wheel positionRequired nameDirection setting in the code
Front leftfrontLeftDriveREVERSE
Front rightfrontRightDriveREVERSE
Back leftbackLeftDriveREVERSE
Back rightbackRightDriveFORWARD

The direction settings account for how the motors are installed. REVERSE here changes how that motor responds to power; it does not mean the robot should drive backward. The code also flips the sideways stick input for this particular robot. Test the actual wheels before changing these settings.

The repository does not record which physical port each motor uses. Check those connections on the robot.

04 / Reading the code

You do not need to understand every Java keyword to follow this file. Read it in these chunks, from top to bottom:

  1. The program's name. The line beginning with @TeleOp gives the Driver Station the name Prototype TeleOp.
  2. Settings. SLOW_MODE_SPEED = 0.4 sets slow-mode power. STRAFE_CORRECTION = 1.1 gives sideways input a small boost to help account for the wheels' less efficient sideways movement.
  3. Motor setup. The lines using hardwareMap.get find the four motors. The code then sets their directions and chooses braking when power is zero, so they resist coasting. It sends power commands without using wheel-rotation measurements to adjust them.
  4. Wait for the driver. waitForStart() waits until START is pressed. Before that, the Driver Station should show “Initialized. Press START.”
  5. Repeat while driving. The section starting with while (opModeIsActive()) runs again and again until the program is stopped. Each pass reads the sticks, works out power for each wheel, and sends it to the motors using setPower.
  6. Show status. The lines using telemetry send information back to the Driver Station. “Telemetry” just means status information—in this case, wheel power commands and whether slow mode is on.

How the wheel powers work

The program combines three requests: forward/backward, sideways, and turning. Each wheel gets a different combination so the robot can move and turn at the same time.

A motor power command is a number from −1 to 1. Zero means no power. The sign chooses a direction; the size chooses the power level. For example, 0.5 asks for half power in that motor's configured positive direction.

When a combination of stick inputs would ask for too much power, the code scales all four wheel commands down together. This keeps them within the allowed range while preserving the balance between them. Holding the bumper reduces them further.

The status display shows the power the code asked for, not the speed the wheels actually reached. A wheel can run differently because of friction, load, or slipping.

05 / Put code on the robot

Building means turning the Java files and FIRST's support code into an installable Android app. Installing puts that app on the robot controller. Use Android Studio for both steps.

  1. Open the whole project. Open the 28150-BIOBUZZ folder in Android Studio, rather than opening just the Java file. The supplied README calls for Android Studio Narwhal 3 Feature Drop or later.
  2. Let setup finish. Android Studio uses a tool called Gradle to prepare and build the project. Let its initial setup, called “sync,” finish. Allow it to download the required development tools when prompted. The first setup needs internet access.
  3. Select TeamCode. Choose TeamCode as the app to build and run. It includes both our code and the required FIRST support code.
  4. Connect the robot controller. Use the team's usual connection method and make sure Android Studio shows the intended device as connected.
  5. Build and install. Use Android Studio's Run button. If there are errors, fix them before trying to drive; the robot may still have an older version installed.
  6. Start from the Driver Station. Confirm the correct hardware configuration is selected. Choose Prototype TeleOp, press INIT, check the ready message, and press START when the robot is ready to test. STOP ends the program.

Optional: build from a terminal

From the project folder, this command builds the app without installing it:

./gradlew :TeamCode:assembleDebug

On Windows, use .\gradlew.bat :TeamCode:assembleDebug. Terminal builds need the Java development tools and Android development tools set up first. For a first build, Android Studio is the easier starting point.

06 / Make a change

Start with a clear goal, such as “make slow mode gentler.” Change one behavior at a time so you can tell what caused the result.

Example: reduce slow-mode power

In PrototypeTeleOp.java, find:

static final double SLOW_MODE_SPEED = 0.4;

Changing 0.4 to 0.3 lowers the slow-mode limit from 40% to 30%. Keep this value between 0 and 1. Leave the rest of the line, including the semicolon, in place. Build, install, and test with the bumper held and released.

Other common changes

  • Adjust sideways driving: change STRAFE_CORRECTION in small steps, then test sideways and diagonal movement. Check wheel setup first if the robot moves in the wrong direction.
  • Rename a motor: change its name in both the Java file and the robot's hardware configuration. Spelling and capital letters must match.
  • Add a robot program: copy a useful example into the TeamCode Java folder. Give the file and the class inside it the same new name. A class is the named block that holds the program. Set a clear name on its @TeleOp line. Remove @Disabled, if present, when the program is ready to appear on the Driver Station.

Save and share your work

Git records changes on your computer. A commit is a saved checkpoint with a description. A push uploads those commits to GitHub so the team can get them.

  1. Before editing, use git status to check for work already in progress. Leave someone else's changes alone; ask before editing a file that already has changes.
  2. Make your change, build it, and test any affected robot behavior. Update this guide if controls or motor names change.
  3. Review the differences. Add only the files for your task to the commit, then check the selected changes before committing.
  4. Write a short commit message explaining what changed, then push to the existing team repository. Do not overwrite Git history or upload someone else's unfinished work.

You can do these steps in Android Studio's Git tools or a terminal. Share completed, checked changes promptly so teammates are working from the same code.

07 / Test your work

A successful build checks whether the code can become an app. It cannot tell whether the motors are connected correctly or the robot drives as intended. This project currently has no automated test suite, so physical testing matters.

  1. Prepare. Make room around the robot and keep STOP within reach. For first wheel-direction checks, securely support the robot with its wheels clear of the ground.
  2. Initialize. Press INIT and confirm the ready message appears without errors.
  3. Start with the sticks released. The robot should stay still.
  4. Test each movement gently. Try forward, backward, both sideways directions, and turning both ways. Then try diagonals and moving while turning.
  5. Test slow mode. Hold and release the right bumper. Check both the robot's response and the ON/OFF message.
  6. Stop. Press STOP and confirm the motors stop. Tell teammates what you tested and whether anything still needs checking.

08 / Fix common problems

ProblemWhat to check first
The project will not build.Read the first error. Let Android Studio finish setup and check that the needed tools downloaded. An error mentioning Java or JAVA_HOME means the build cannot find the Java tools.
Prototype TeleOp is missing.Confirm you installed the latest TeamCode app on the correct controller. Check the program's @TeleOp name and make sure it has no @Disabled line.
INIT says a motor cannot be found.Compare the four motor names above with the selected hardware configuration. Check spelling, device type, and which configuration is active.
A wheel spins the wrong way.Check that the name points to the correct physical wheel, then check its direction setting. Change one thing at a time.
The robot moves sideways the wrong way.Check wheel placement and motor directions before changing the sideways input sign. This program already includes an adjustment for this robot's setup.
The robot drifts.Check for slipping, rubbing, uneven weight, or wheel problems. Equal power commands do not guarantee equal wheel speed.
