01 / What is here

This repository builds an Android Robot Controller application for team 28150. It is based on the public FTC SDK for the BIOBUZZ 2026–2027 season. The team's custom behavior currently lives in PrototypeTeleOp.java: a driver-operated, robot-centric mecanum drivetrain.

1team Java OpMode
4drive motors
40%slow-mode power scale

The code reads the first gamepad, mixes translation and rotation into four wheel powers, and sends those commands through the FTC hardware APIs. It also reports commanded powers and slow-mode status to the Driver Station.

There is no team autonomous routine, field-relative control, IMU integration, vision pipeline, mechanism control, or encoder-based navigation in the current team code. The SDK includes examples of many of these features; their presence does not mean the robot uses them.

Documentation distinction. The existing README.md is largely SDK documentation and release history. The TeamCode template readme still says the module is empty; the actual Java source contains the prototype described here. This guide documents that source.

03 / How it runs

Build-time structure

TeamCode app + team Java→FtcRobotController library→FTC Maven dependencies→Robot Controller APK

TeamCode is the installable application module, even though FtcRobotController has the controller-oriented name. The app ID is com.qualcomm.ftcrobotcontroller. The shared build reads app version 12.0 and version code 63 from the controller manifest.

Runtime structure

The Android launcher enters PermissionValidatorWrapper; the controller activity sets up the controller UI and SDK services. Its startup processes classes for OpMode discovery and creates the FTC event loop using the selected hardware configuration. The SDK manages communication with the Driver Station and exposes gamepad inputs, hardware objects, and telemetry to the team code.

Driver Station / gamepad→FTC runtime→PrototypeTeleOp→DcMotor commands

The annotation @TeleOp(name = "Prototype TeleOp", group = "Prototype") makes the class discoverable in the Driver Station's TeleOp list. There is no @Disabled annotation. The SDK's manual registration file is intentionally empty; normal team OpModes use annotations.

The OpMode lifecycle

  1. INIT: runOpMode() retrieves all four motors by name, applies directions, enables BRAKE, and selects RUN_WITHOUT_ENCODER.
  2. Ready: telemetry displays “Initialized. Press START.” The call to waitForStart() waits for the start signal.
  3. START: while opModeIsActive(), the code reads gamepad1, calculates power, writes all four motors, and updates telemetry.
  4. STOP: the active loop exits and the FTC runtime handles OpMode shutdown. The class contains no separate cleanup method or explicit final zero-power block.

A robot's selected device configuration is an external runtime input. No tracked robot configuration in this checkout defines motor ports or hub assignments. Those must be checked on the actual controller.

04 / Hardware & controls

Hardware names are a contract: each string below must match a configured DcMotor device exactly. Names identify logical wheel positions; physical port numbers are not specified in the source.

All four use BRAKE for zero-power behavior and RUN_WITHOUT_ENCODER. Braking resists coasting; it does not implement position holding. This program does not read encoder positions or regulate wheel velocity with feedback.

gamepad1 inputBehavior
Left stick YForward/backward; the raw Y value is negated.
Left stick XStrafe; the raw X value is negated and multiplied by 1.1.
Right stick XRotation input.
Hold right bumperScale final wheel commands to 0.4. Releasing restores 1.0.
Robot-specific setup: three motors are reversed, and strafe has an extra sign inversion. The source comment says this drivetrain strafes opposite to the standard mecanum layout. Preserve these choices until physical testing supports a change. The repository does not establish wheel roller orientation or wiring.

“Robot-centric” means translation stays relative to the chassis. After the robot turns, pushing forward drives toward its new front. There is no heading measurement or coordinate rotation to keep commands aligned with the field.

05 / Drive calculations

Each loop begins with three inputs and one power scale:

y  = -gamepad1.left_stick_y
x  = -gamepad1.left_stick_x * 1.1
rx =  gamepad1.right_stick_x
speed = gamepad1.right_bumper ? 0.4 : 1.0

denominator = max(abs(y) + abs(x) + abs(rx), 1)

frontLeftPower  = (y + x + rx) / denominator * speed
backLeftPower   = (y - x + rx) / denominator * speed
frontRightPower = (y - x - rx) / denominator * speed
backRightPower  = (y + x - rx) / denominator * speed

Forward motion contributes equally to all wheel commands. Strafe contributes opposite signs to the two diagonals. Rotation contributes opposite signs to the left and right sides. Dividing by the common denominator preserves the mix while keeping command magnitudes at or below the selected power scale.

The 1.1 strafe correction increases strafe contribution before normalization. At full pure strafe, normalization brings commands back to magnitude 1; it does not produce 110% motor power. Slow mode multiplies the normalized values, so 40% describes commanded power, not a guaranteed physical speed.

Raw stick input, normal modeFLFRBLBR
Left Y = −1; others 01111
Left X = +1; others 0−111−1
Right X = +1; others 01−11−1
Left Y = −1, right X = +1; left X = 01010

These are logical setPower() values, before configured motor direction affects physical rotation. With the bumper held, multiply every entry by 0.4. Actual movement depends on wheel installation, wiring, load, and traction.

Telemetry reports the calculated powers, not measured wheel speed. The current loop has no custom joystick deadband, acceleration limiting, heading hold, or closed-loop correction.

07 / Making changes

Choose the right place

Make robot behavior changes under TeamCode/src/main/java/org/firstinspires/ftc/teamcode/. Keep the package declaration consistent with that path. For a new OpMode, copy a relevant SDK sample, rename the public class and file together, set a distinct @TeleOp or @Autonomous name, and remove @Disabled only when it should be selectable. Avoid manual registration changes.

08 / Verification

Software checks

No dedicated unit or instrumentation test suite was found. The files named UtilityTestHardware and UtilityTestGamepad are SDK diagnostic OpModes, not automated tests. There is also no tracked CI workflow in this checkout. Use :TeamCode:assembleDebug for compilation and :TeamCode:lintDebug for Android static analysis; record environment blockers and existing failures accurately.

If drive mixing is later extracted into a pure calculation method, useful automated tests would check normalization, zero input, rotation/strafe signs, combined axes, and the 0.4 scale. They would verify arithmetic, while actual wheel behavior still needs robot testing.

Robot acceptance sequence

  1. Before START: confirm the device, APK, hardware configuration, motor names, physical wheel mapping, and accessible STOP control. For initial direction checks, securely support the robot with wheels clear and keep people clear of moving parts.
  2. INIT: confirm the ready message and no hardware lookup errors. All four mappings must resolve before driving starts.
  3. Neutral: start with sticks released; confirm no commanded motion. This program adds no custom deadband.
  4. Individual actions: test forward, reverse, both strafes, and both rotation directions at low power. Check telemetry against the command table before changing signs.
  5. Combined actions: test diagonals and translation with rotation. Confirm power magnitudes stay bounded and steering remains predictable.
  6. Slow mode: hold and release the bumper. Confirm telemetry changes ON/OFF and power scales to 0.4 of the normal command for the same inputs.
  7. STOP and restart: verify motion ceases promptly, then reinitialize and retest. Record tested conditions, observed behavior, and remaining limitations with the change.

09 / Troubleshooting

The build stops before compiling

Check Java availability first (java -version and JAVA_HOME), then Android SDK location, required packages, and dependency network access. Use the checked-in wrapper. This guide's build attempt stopped at the Java check; later stages were not reached.

Prototype TeleOp does not appear

Check that the class is in TeamCode, has the expected @TeleOp annotation, and is not disabled. Confirm that a successfully rebuilt TeamCode APK was installed on the intended controller and that the Driver Station is connected to it.

INIT reports a missing device

Compare the exact hardwareMap name and expected DcMotor type against the active controller configuration. Check spelling and case, and confirm the correct configuration is selected. The source alone cannot identify the right physical port.

One wheel or one movement axis is wrong

Verify logical-to-physical wheel mapping, wheel roller layout, and motor directions first. Then compare the joystick sign transforms and mixing equations. This robot deliberately uses three reversed motors and an inverted strafe input; changing several signs at once makes the fault harder to isolate.

The robot drifts or does not travel straight

Check mechanical friction, traction, wheel orientation, loading, and motor consistency. The current drive is open loop; equal power does not guarantee equal wheel speed or distance. The strafe correction is a fixed tuning factor, not measured position correction.

SDK examples compile but the team's feature is absent

Samples are reference programs, many disabled by annotation. Copy and adapt a sample into TeamCode, configure the actual hardware, and enable only the intended OpMode. Including Vision or other SDK dependencies does not itself add a team vision or autonomous feature.

10 / Future development

The current design is small enough to read end to end. Expand it when there is a concrete robot requirement:

  • Shared hardware setup: extract common mapping and initialization when multiple OpModes need the same robot.
  • Drive calculation helper: separate arithmetic from hardware writes when independent math tests or reuse becomes useful.
  • Mechanisms: introduce clear ownership of each motor/servo and define limits, controller mappings, and shutdown behavior.
  • Autonomous: add an @Autonomous entry point with bounded actions and stop checks, then choose sensing and localization to match the task.
  • Field-relative driving: requires an IMU, configured mounting orientation, a heading reference, and a coordinate transform; it is not a parameter switch in the current code.
  • Vision: requires a configured camera, processing setup, and decisions about how detections affect control. Adapt the SDK 12.0 samples rather than assuming older AprilTag APIs still match.

These are possible extensions, not existing subsystems or a required roadmap. The SDK README documents a 12.0 breaking change in AprilTag detection handling for single tags versus clusters; consult that release information before adapting older vision code.
